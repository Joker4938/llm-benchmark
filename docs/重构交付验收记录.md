## 4. 完全断网启动演练

使用独立临时目录、容器名、数据卷和端口进行演练，未接触真实部署数据。流程如下：

1. 使用 `docker save` 生成本地镜像归档；
2. 生成并校验 SHA-256；
3. 执行 `install.sh`，确认只通过 `docker load` 加载本地镜像；
4. 为临时 Compose 网络设置 `internal: true`，阻断公网出口；
5. 执行 `run.sh`，等待容器健康；
6. 验证 `/health/live` 和 `/health/ready`；
7. 在同一隔离网络内访问首页，完成登录和会话验证；
8. 在容器内执行 `python -m benchmark_cli --help`；
9. 尝试访问公网地址，确认因无法解析/连接而失败。

验收结果：

- API 和 executor 均正常启动；
- readiness 返回数据库可用、数据目录可写、executor 心跳正常、配置有效；
- 首页返回 200；
- 登录和 `/api/auth/verify` 返回 200；
- CLI 在无浏览器、无公网环境中可启动；
- 运行过程不需要下载 Python、Node、字体、脚本或其他公网资源。

## 5. 更新失败自动回滚演练

通过基于正式镜像制作的故障镜像进行健康检查失败注入。故障镜像可以执行严格数据库迁移，但不会启动 HTTP 服务，因此新版健康检查必然超时。

首次演练发现：Python `tarfile` 的安全 `data` 过滤器不会恢复归档属主，导致回滚后的 `secret.key` 属于 root，非特权运行用户无法读取。该问题已在提交 `3647b8a` 中修复：恢复数据后将数据目录及其内容统一恢复为运行时 UID/GID `10001:10001`，并增加回归测试。

修复后的演练结果：

- `update.sh` 在修改数据前创建完整数据归档和 SHA-256；
- 新版离线镜像加载和严格迁移成功；
- 新版健康检查按预期失败，脚本返回非零退出码；
- 自动停止并移除故障容器；
- 自动恢复旧 `.env`、`docker-compose.yml`、镜像标签和数据卷内容；
- 演练前写入的数据标记在回滚后仍存在；
- `secret.key` 的 UID/GID 恢复为 `10001:10001`；
- 旧版本重新进入 `healthy`，readiness 通过。
