# 完全离线部署说明

本文说明如何在**无法访问互联网的企业内网服务器**上安装、运行、停止和更新 LLM Benchmark。目标服务器只负责运行容器；镜像构建、依赖下载和部署包制作必须在具备完整依赖的构建环境中完成。

运行期间不会访问 Docker Hub、PyPI、npm registry、CDN、公网字体或遥测服务。被测 OpenAI 兼容模型端点必须能从目标服务器所在网络访问。

## 1. 部署边界

- 部署形态：单台服务器、单个应用容器、一个 Docker 命名卷；
- 服务组成：FastAPI API 与本地 executor 由容器内 supervisor 共同管理；
- 数据存储：SQLite、报告和本地密钥材料均保存在数据卷；
- Web 客户端：Windows 7 仅作为浏览器客户端，建议 Chrome 109 或 Firefox 115 ESR；
- 登录用途：避免内网无关人员误用或滥用，不提供多租户权限体系；
- 不支持 Internet Explorer；
- 目标服务器不执行源码构建，也不需要 Python、Node.js、PyPI 或 npm。

## 2. 目标服务器要求

目标服务器应预先具备：

- Docker Engine；
- Docker Compose 插件，可执行 `docker compose version`；
- POSIX shell；
- `awk`、`od`、`tr`、`date` 等常用系统命令；
- `sha256sum` 或 `shasum`；
- 足够的镜像、数据卷、报告和更新备份空间。

部署用户必须能访问 Docker daemon。可在部署前执行：

```bash
docker info
docker compose version
```

这两个命令都应成功，且不应触发任何联网下载。

## 3. 离线部署包

建议交付包保持以下结构：

```text
llm-benchmark/
├── images/
│   └── llm-benchmark-<version>.tar
├── checksums.sha256
├── docker-compose.yml
├── .env.example
├── install.sh
├── run.sh
├── stop.sh
└── update.sh
```

部署生命周期只使用四个脚本：

| 脚本 | 用途 | 是否自动启动服务 |
| --- | --- | --- |
| `install.sh` | 校验并加载镜像，生成本机配置，创建数据卷 | 否 |
| `run.sh` | 使用本地镜像启动服务并等待健康 | 是 |
| `stop.sh` | 优雅停止服务，保留容器和数据 | 否 |
| `update.sh` | 备份、迁移、切换新版，失败时自动回滚 | 是 |

不要把生成后的 `.env`、数据卷内容、`backups/` 或登录凭据放入通用部署包。

## 4. 在构建环境制作部署包

以下操作在可获得源码、依赖和 Docker 基础镜像的构建环境中执行，而不是在隔离内网服务器上执行。

```bash
docker build -t llm-benchmark:0.1.0 .
mkdir -p release/images
docker save -o release/images/llm-benchmark-0.1.0.tar llm-benchmark:0.1.0
cp docker-compose.yml .env.example install.sh run.sh stop.sh update.sh release/
cd release
sha256sum images/llm-benchmark-0.1.0.tar > checksums.sha256
```

macOS 可用以下命令生成相同格式的校验文件：

```bash
shasum -a 256 images/llm-benchmark-0.1.0.tar > checksums.sha256
```

将整个 `release/` 目录通过组织允许的离线介质传入目标服务器。传输完成后，建议再次校验介质和文件完整性。

## 5. 首次安装

进入部署目录并授予脚本执行权限：

```bash
chmod +x install.sh run.sh stop.sh update.sh
./install.sh
```

`install.sh` 按以下顺序执行：

1. 检查 Docker、Docker Compose 和脚本依赖命令；
2. 定位离线镜像归档；
3. 校验镜像归档 SHA-256；
4. 通过 `docker load` 加载镜像，不执行在线拉取；
5. 从 `.env.example` 创建本机 `.env`，并设置权限为 `600`；
6. 写入实际加载的镜像标签；
7. 首次安装时生成随机登录密码；
8. 生成至少 16 个字符的随机会话密钥；
9. 创建 Docker 命名卷和权限为 `700` 的 `backups/` 目录；
10. 输出初始用户名、密码和下一步启动命令。

安装脚本**不会自动启动服务**，便于管理员先核对 `.env`、监听地址和端口。

### 5.1 镜像归档选择

默认按以下位置查找归档：

1. `images/llm-benchmark-*.tar`；
2. 部署目录根部的 `llm-benchmark-*.tar`；
3. 部署目录根部的 `llm-benchmark.tar`。

如果发现多个归档，脚本会拒绝猜测。请显式指定：

```bash
LLM_BENCHMARK_IMAGE_ARCHIVE='images/llm-benchmark-0.1.0.tar' ./install.sh
```

也可使用绝对路径。若归档中的镜像标签无法自动识别，或希望指定其中某个标签，可同时设置：

```bash
LLM_BENCHMARK_IMAGE='llm-benchmark:0.1.0' \
LLM_BENCHMARK_IMAGE_ARCHIVE='images/llm-benchmark-0.1.0.tar' \
./install.sh
```

### 5.2 SHA-256 校验文件

校验文件选择顺序为：

1. 环境变量 `LLM_BENCHMARK_CHECKSUM_FILE` 指定的文件；
2. 部署目录中的 `checksums.sha256`；
3. 与归档相邻的 `<归档文件>.sha256`。

示例：

```bash
LLM_BENCHMARK_CHECKSUM_FILE='checksums-0.1.0.sha256' \
LLM_BENCHMARK_IMAGE_ARCHIVE='images/llm-benchmark-0.1.0.tar' \
./install.sh
```

校验值不匹配时安装会立即终止，不会加载损坏或被替换的归档。

### 5.3 登录凭据

首次生成密码时，终端会打印初始用户名和密码。请立即保存到组织认可的凭据管理位置。密码不会在后续重复安装时再次打印。

如需自定义凭据，可在启动前编辑 `.env`：

```dotenv
LLM_BENCHMARK_USER=admin
LLM_BENCHMARK_PASSWORD=replace-with-a-local-password
LLM_BENCHMARK_SESSION_SECRET=replace-with-at-least-16-characters
```

`.env` 必须只保存在部署服务器，不得提交到 Git 或随通用部署包分发。

## 6. 环境变量

`.env.example` 提供以下配置：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `LLM_BENCHMARK_IMAGE` | `llm-benchmark:latest` | 当前应用镜像标签，安装/更新脚本会维护 |
| `LLM_BENCHMARK_CONTAINER_NAME` | `llm-benchmark` | 容器名称 |
| `LLM_BENCHMARK_DATA_VOLUME` | `llm-benchmark-data` | 持久化数据卷名称 |
| `LLM_BENCHMARK_BIND_ADDRESS` | `0.0.0.0` | Web 监听地址；仅本机访问时可设为 `127.0.0.1` |
| `LLM_BENCHMARK_WEB_PORT` | `8080` | 宿主机 Web 端口 |
| `LLM_BENCHMARK_USER` | `admin` | 简单登录用户名 |
| `LLM_BENCHMARK_PASSWORD` | 首次安装生成 | 登录密码，不能为空 |
| `LLM_BENCHMARK_SESSION_SECRET` | 首次安装生成 | 会话签名密钥，至少 16 个字符 |
| `LLM_BENCHMARK_SESSION_HOURS` | `12` | 登录会话有效时长 |
| `LLM_BENCHMARK_SECURE_COOKIE` | `false` | 仅通过 HTTPS 访问时设为 `true` |

脚本还接受以下一次性运行变量：

| 变量 | 默认值 | 使用脚本 | 说明 |
| --- | --- | --- | --- |
| `LLM_BENCHMARK_IMAGE_ARCHIVE` | 自动查找 | `install.sh`、`update.sh` | 指定离线镜像归档 |
| `LLM_BENCHMARK_CHECKSUM_FILE` | `checksums.sha256` | `install.sh`、`update.sh` | 指定校验文件 |
| `LLM_BENCHMARK_NEW_IMAGE` | `docker load` 识别结果 | `update.sh` | 指定新版镜像标签 |
| `LLM_BENCHMARK_HEALTH_TIMEOUT` | `120` 秒 | `run.sh`、`update.sh` | 健康检查等待上限，必须为正整数 |
| `LLM_BENCHMARK_STOP_TIMEOUT` | `30` 秒 | `stop.sh`、`update.sh` | 优雅停止宽限时间，必须为正整数 |

如果通过 HTTPS 反向代理访问，请让代理连接容器暴露的 HTTP 端口，并设置：

```dotenv
LLM_BENCHMARK_SECURE_COOKIE=true
```

如果仍通过普通 HTTP 访问，不要启用安全 Cookie，否则浏览器不会发送登录会话 Cookie。

## 7. 启动与健康检查

执行：

```bash
./run.sh
```

启动脚本会：

1. 验证 `.env` 中用户名、密码和会话密钥；
2. 验证会话密钥至少 16 个字符；
3. 确认配置的镜像已存在于本地；
4. 使用 `docker compose up --detach --no-build` 启动，既不构建也不拉取；
5. 等待容器 healthcheck 进入 `healthy`；
6. 异常或超时时输出最后 80 行日志。

默认等待 120 秒。较慢服务器可临时延长：

```bash
LLM_BENCHMARK_HEALTH_TIMEOUT=240 ./run.sh
```

默认访问地址：

```text
http://<服务器IP>:8080
```

本机健康检查：

```bash
curl http://127.0.0.1:8080/health/live
curl http://127.0.0.1:8080/health/ready
```

- `/health/live` 表示 API 进程仍可响应；
- `/health/ready` 还会检查服务是否具备接收任务的条件，包括 executor 状态。

查看容器状态和日志：

```bash
docker compose --env-file .env -f docker-compose.yml ps
docker compose --env-file .env -f docker-compose.yml logs --tail 200
docker compose --env-file .env -f docker-compose.yml logs -f
```

## 8. 停止与再次运行

执行：

```bash
./stop.sh
```

`stop.sh` 使用 Compose `stop` 发起优雅停止，默认宽限 30 秒。可临时调整：

```bash
LLM_BENCHMARK_STOP_TIMEOUT=60 ./stop.sh
```

停止操作保留容器、镜像和数据卷。再次执行以下命令即可恢复服务：

```bash
./run.sh
```

**不要执行 `docker compose down -v`。** `-v` 会删除数据卷，导致数据库、报告、API 配置和密钥材料丢失。

## 9. 数据持久化与备份

默认 Docker 命名卷为：

```text
llm-benchmark-data
```

容器内挂载点为 `/app/data`，主要包含：

```text
/app/data/llm-benchmark.db
/app/data/reports/
/app/data/本地加密密钥材料
```

查看卷信息：

```bash
docker volume inspect llm-benchmark-data
```

不要在服务运行时直接修改 SQLite 文件或报告目录。更新脚本会先停止旧服务，再创建一致性数据卷备份。

建议将部署目录中的 `backups/` 纳入内网备份制度，并确保备份介质的访问权限不低于 `.env` 和数据卷；其中可能包含凭据密文、报告和请求结果。

## 10. 离线更新与自动回滚

将新版镜像归档及校验文件放入部署目录，然后执行：

```bash
LLM_BENCHMARK_IMAGE_ARCHIVE='images/llm-benchmark-0.3.0.tar' ./update.sh
```

如果归档包含多个镜像标签或无法自动识别目标标签，显式指定：

```bash
LLM_BENCHMARK_IMAGE_ARCHIVE='images/llm-benchmark-0.3.0.tar' \
LLM_BENCHMARK_NEW_IMAGE='llm-benchmark:0.3.0' \
./update.sh
```

更新前必须已执行过 `install.sh`，且当前 `.env`、旧镜像和数据卷必须存在。更新流程为：

1. 校验新版镜像归档；
2. 记录当前镜像标签和不可变镜像 ID；
3. 创建带 UTC 时间戳的 rollback 镜像标签；
4. 停止旧服务；
5. 使用旧应用镜像内的 Python `tarfile` 备份完整数据卷；
6. 保存数据备份 SHA-256、`.env`、`docker-compose.yml` 和旧镜像信息；
7. 加载新版镜像并更新 `.env` 中的镜像标签；
8. 以 `--network none` 启动一次性容器，执行严格数据库初始化/迁移；
9. 启动新版并等待 readiness 健康检查；
10. 保存新版日志、镜像标签和镜像 ID。

数据备份与数据库迁移容器都使用 `--network none`，不会因更新流程访问公网。

每次更新的备份目录格式为：

```text
backups/update-<UTC时间戳>/
```

其中会保留：

- `data.tar.gz` 及其 SHA-256；
- 更新前的 `.env`；
- 更新前的 `docker-compose.yml`；
- 旧镜像标签、旧镜像 ID 和 rollback 标签；
- 新镜像标签和 ID（成功时）；
- 新版本日志；
- 自动回滚失败时的旧版本日志。

### 10.1 失败时发生什么

从旧服务停止并创建备份后，更新脚本会进入自动回滚保护。后续任一步骤失败时，脚本会尝试：

1. 保存新版本诊断日志；
2. 停止并移除失败的新版本容器；
3. 清空并恢复完整数据卷；
4. 恢复更新前的 `.env`；
5. 恢复更新前的 `docker-compose.yml`；
6. 恢复旧镜像标签，必要时改用保留的 rollback 标签；
7. 重新启动旧版本；
8. 等待旧版本健康检查通过。

看到以下信息表示自动回滚成功：

```text
[回滚] 已恢复旧数据、旧配置和旧镜像，旧版本健康检查通过。
```

如果提示“自动回滚未完全成功”，不要删除备份目录或数据卷。先查看终端输出以及对应 `backups/update-.../` 下的日志，再按故障排查文档执行人工恢复。

## 11. Compose 运行与安全设置

项目的 `docker-compose.yml` 已固定以下离线与安全行为：

- `pull_policy: never`，禁止自动拉取镜像；
- 不包含 `build:`，目标服务器不进行源码构建；
- 单应用服务和单命名数据卷；
- readiness healthcheck；
- `restart: unless-stopped`；
- `init: true`，正确转发并回收子进程；
- 删除全部 Linux capabilities：`cap_drop: ALL`；
- `no-new-privileges:true`；
- `/tmp` 使用 64 MB tmpfs；
- JSON 日志单文件最多 10 MB，最多保留 3 个文件；
- 容器停止宽限时间 30 秒。

这些设置不能替代内网访问控制。仍应通过服务器防火墙限制访问来源，并避免把服务端口暴露到不受信任网络。

## 12. 完全离线验收

建议在正式交付前使用与生产相同的隔离条件进行验收：

1. 禁止目标服务器访问互联网；
2. 确认本机不存在需要在线拉取的应用镜像；
3. 执行 `./install.sh`，确认仅加载部署包中的归档；
4. 执行 `./run.sh`，确认不触发 build 或 pull；
5. 验证 `/health/live` 和 `/health/ready`；
6. 用浏览器登录并创建一个小规模 `smoke` 任务；
7. 确认 executor 可领取任务并生成报告；
8. 停止并重新运行服务，确认任务记录和报告仍存在；
9. 检查应用与 Docker 日志，确认没有公网域名请求或资源加载失败；
10. 使用测试版本执行一次成功更新和一次故意失败更新，确认自动回滚后旧版本仍健康且数据可用。

浏览器开发者工具的 Network 面板中，页面资源应全部来自部署服务器；页面不应加载 CDN、远程字体、遥测脚本或公网 API。

## 13. 日常运维建议

- 修改 `.env` 前先创建权限受限的副本；
- 定期检查数据卷、Docker 日志和 `backups/` 的磁盘占用；
- 更新成功后先保留 rollback 镜像和更新备份，完成业务验收后再按组织策略清理；
- 不要直接编辑数据卷中的数据库；
- 不要提交或发送 `.env`、数据库、加密密钥和包含真实提示词的报告；
- 仅使用部署包中的四个脚本完成生命周期操作；
- 遇到启动、健康检查、模型端点或回滚问题时，参见 `docs/故障排查.md`（该文档随任务 8.6 后续子闭环补充）。
