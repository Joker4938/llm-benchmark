# 旧版本迁移说明

本文说明如何从旧版 Flask、Vue 2、Element UI、Streamlit 和文件型报告实现迁移到当前 FastAPI、Vue 3、SQLite 与本地 executor 架构，并说明自动迁移、容错启动和部署更新回滚之间的区别。

迁移的首要原则是：**先备份、保留原文件、让新版本可运行，再验证迁移结果。** 即使某一旧文件迁移失败，也不应阻止新版本启动；但“服务可启动”不等于“所有旧数据已完整恢复”，管理员仍需检查诊断信息和迁移记录。

## 1. 迁移范围

### 1.1 自动迁移的数据

当前自动迁移器处理：

- 旧 API 配置文件 `backend/api_configs.json`；
- 旧 `reports/` 目录中的普通文件；
- 新版 SQLite 自身的 schema 版本升级。

### 1.2 不自动迁移的数据

以下旧状态不会转换为新版持久任务：

- Flask 进程内存中的运行中任务；
- 旧页面刷新后本来就会丢失的临时状态；
- Flask JWT 或其他旧登录会话；
- Streamlit session state；
- 浏览器本地缓存、表单草稿和 Element UI 页面状态；
- 无法从旧报告可靠推导出的新指标、事件序列、断言和阈值结论。

迁移前应让旧压测任务正常结束，并导出仍需保留的结果。新版本启动后需要重新登录。

### 1.3 兼容入口

旧命令入口目前作为兼容包装保留：

```text
llm_benchmark.py
run_benchmarks.py
```

新自动化脚本应优先迁移到：

```bash
python3 -m benchmark_cli --help
```

不要继续依赖旧 Flask API 或 Streamlit 页面；新 Web 功能验收完成后，这些重复实现会从生产代码中移除。

## 2. 新旧架构映射

| 旧实现 | 新实现 | 迁移方式 |
| --- | --- | --- |
| Flask API 与进程内任务状态 | FastAPI + SQLite 持久队列 | 不迁移运行中状态，重新提交任务 |
| `backend/api_configs.json` | SQLite `api_configs` | 启动时自动读取并加密写入 |
| `reports/` 文件 | SQLite 报告索引 + 本地报告目录 | 按文件登记；建议先复制到新报告目录 |
| Vue 2 + Element UI | Vue 3 + 原生组件样式 | 不迁移页面状态 |
| Streamlit `webui.py` | Vue 3 Web 界面 | 不迁移会话状态 |
| 旧脚本参数 | `benchmark_cli` | 兼容入口过渡，逐步改用新 CLI |
| 文件/内存状态 | `/app/data/llm-benchmark.db` | 首次启动初始化 schema |

## 3. 迁移前准备

### 3.1 停止旧版本写入

迁移前停止旧服务，确保配置和报告不再变化。不要在旧程序仍写报告时复制目录。

### 3.2 创建原始备份

至少保留：

```text
backend/api_configs.json
reports/
旧版本环境配置
旧版本镜像标签或源码提交
```

示例：

```bash
stamp=$(date -u '+%Y%m%dT%H%M%SZ')
mkdir -p "migration-backup-$stamp"
cp -p backend/api_configs.json "migration-backup-$stamp/" 2>/dev/null || true
cp -R reports "migration-backup-$stamp/" 2>/dev/null || true
```

备份可能包含明文 API Key、真实提示词和模型响应，必须限制访问权限并使用组织认可的离线介质。

### 3.3 检查旧 API 配置

旧配置根节点必须是 JSON 数组。每项应至少具备可用的端点和模型字段，例如：

```json
[
  {
    "id": "local-model",
    "name": "内网模型",
    "llm_url": "http://10.0.0.20:8000/v1",
    "api_key": "replace-me",
    "model": "internal-model",
    "timeout": 60,
    "verify_tls": false
  }
]
```

可在迁移前离线检查 JSON：

```bash
python3 -m json.tool backend/api_configs.json >/dev/null
```

若文件中存在失效或不应继续使用的 API Key，先在目标服务端轮换密钥，再迁移新值。

### 3.4 估算空间

迁移和更新期间可能同时存在：

- 原始旧文件；
- 新数据卷；
- 完整数据卷压缩备份；
- 旧镜像、rollback 标签和新版镜像。

磁盘空间不足可能让迁移、报告写入或自动回滚同时失败。正式操作前应检查 Docker 数据目录和部署目录的剩余空间。

## 4. 自动迁移机制

FastAPI 和独立 executor 初始化时会执行 `LegacyMigrator`。默认输入路径为：

```text
backend/api_configs.json
reports/
```

可通过环境变量覆盖：

```text
LLM_BENCHMARK_LEGACY_CONFIG
LLM_BENCHMARK_LEGACY_REPORTS
```

自动迁移流程：

1. 初始化或升级新版 SQLite schema；
2. 加载本地 API Key 加密密钥；
3. 扫描旧 API 配置文件；
4. 扫描旧报告目录中的普通文件；
5. 按“源文件绝对路径 + 内容 SHA-256”查询迁移记录；
6. 已成功迁移且内容未变化的文件记为 `skipped`；
7. 成功项记为 `migrated`；
8. 失败项记录脱敏错误并记为 `failed`；
9. 无论单个旧文件成功或失败，启动流程继续。

迁移结果可在登录后的诊断接口或设置/诊断页面查看：

```text
GET /api/diagnostics
```

响应中的 `legacy_migration` 会显示本次扫描的 `migrated`、`skipped` 和 `failed` 数量。

## 5. API 配置迁移

### 5.1 字段映射

旧配置按以下规则转换：

| 旧字段 | 新字段 | 说明 |
| --- | --- | --- |
| `id` | `id` | 有值时尽量保留；无值时生成新 ID |
| `name` | `name` | 缺失时生成 `legacy-<序号>` |
| `llm_url` 或 `base_url` | `base_url` | 兼容两种旧命名 |
| `model` | `model` | 原值保留 |
| `api_key` | API Key 密文 | 迁移时使用本地 `SecretBox` 加密 |
| `verify_tls` | `verify_tls` | 旧值缺失时按兼容行为处理 |
| `timeout` | `timeout_seconds` | 默认 60 秒 |
| `is_default` | `is_default` | 转换为布尔值 |

迁移后 Web API 不返回完整 API Key，只返回是否已配置及指纹等安全信息。

### 5.2 验证步骤

1. 登录新 Web；
2. 打开“测试资源/API 配置”；
3. 核对名称、Base URL、模型、TLS 和超时；
4. 对每个重要端点执行小规模 `smoke`；
5. 确认成功后再考虑安全归档或销毁旧明文配置。

自动迁移不会删除或改写原 `backend/api_configs.json`。

## 6. 旧报告迁移

### 6.1 登记方式

迁移器逐个读取旧报告文件并计算：

- 文件格式后缀；
- 文件大小；
- SHA-256；
- 原文件路径。

JSON 文件会先执行 JSON 语法校验。无法解析的 JSON 记录为失败，不影响其他文件。

旧报告不会被改写成新报告 schema，也不会凭空补齐 TTFT、窗口事件、断言结果或 Token 来源。缺失字段应保持不可用，不能用零值或推测值填充。

### 6.2 推荐放置方式

为确保迁移后的报告能通过新版路径安全检查下载，建议先把旧报告复制到新版报告根目录：

```text
<数据目录>/reports/
```

源码运行时，如果 `LLM_BENCHMARK_DATA_DIR=./data`：

```bash
mkdir -p data/reports
cp -R reports/. data/reports/
export LLM_BENCHMARK_LEGACY_REPORTS="$(pwd)/data/reports"
```

容器部署时，新报告根目录为：

```text
/app/data/reports
```

不要只登记一个稍后会删除或卸载的外部路径；迁移索引不会替代原文件内容。自动迁移也不会删除原报告。

### 6.3 同名文件

复制旧报告时不要覆盖新版本已经生成的同名文件。建议迁移到独立子目录：

```text
/app/data/reports/legacy-<日期>/
```

迁移器会扫描所指定目录的直接子文件；如需迁移分层目录，应按目录分批处理，或先整理为不会重名的单层暂存目录。

## 7. 源码部署迁移流程

适用于从旧源码运行方式迁移到新的源码环境。

### 7.1 准备新数据目录

```bash
mkdir -p data/reports
cp -p backend/api_configs.json data/legacy-api-configs.json
cp -R reports/. data/reports/
chmod 700 data
```

### 7.2 设置环境变量

```bash
export LLM_BENCHMARK_USER='admin'
export LLM_BENCHMARK_PASSWORD='replace-me'
export LLM_BENCHMARK_SESSION_SECRET='replace-with-at-least-16-characters'
export LLM_BENCHMARK_DATA_DIR="$(pwd)/data"
export LLM_BENCHMARK_LEGACY_CONFIG="$(pwd)/data/legacy-api-configs.json"
export LLM_BENCHMARK_LEGACY_REPORTS="$(pwd)/data/reports"
```

### 7.3 首次启动

分别启动 API 与 executor，或先只启动 API 检查迁移结果：

```bash
python3 -m uvicorn benchmark_server.main:app --host 127.0.0.1 --port 8080
```

登录后查看诊断页面和资源列表。确认迁移完成后，再启动 executor：

```bash
python3 -m benchmark_server.executor_main
```

API 和 executor 都可能执行相同迁移扫描；路径与 SHA-256 去重保证已成功文件不会重复处理。

## 8. Docker 离线部署迁移流程

新版生产容器默认只挂载 `/app/data`，不会自动看到宿主机任意旧路径。因此需要先把旧文件放入数据卷可访问的位置。

### 8.1 先完成新版本安装

```bash
./install.sh
```

安装不会启动服务。

### 8.2 把旧文件复制进数据卷

下面使用已加载的应用镜像作为离线工具容器。先从 `.env` 获取镜像和卷名：

```bash
image=$(awk -F= '$1=="LLM_BENCHMARK_IMAGE" {print substr($0, index($0, "=") + 1)}' .env)
volume=$(awk -F= '$1=="LLM_BENCHMARK_DATA_VOLUME" {print substr($0, index($0, "=") + 1)}' .env)
```

假设旧 `backend/` 和 `reports/` 已复制到当前部署目录，使用只读 bind mount 把它们转存到命名卷：

```bash
docker run --rm --user 0:0 --network none \
  --entrypoint python \
  --volume "$volume:/app/data" \
  --volume "$(pwd)/backend/api_configs.json:/legacy/api_configs.json:ro" \
  --volume "$(pwd)/reports:/legacy/reports:ro" \
  "$image" \
  -c 'import os, pathlib, shutil
source_config = pathlib.Path("/legacy/api_configs.json")
source_reports = pathlib.Path("/legacy/reports")
target_config = pathlib.Path("/app/data/legacy/api_configs.json")
target_reports = pathlib.Path("/app/data/reports")
target_config.parent.mkdir(parents=True, exist_ok=True)
target_reports.mkdir(parents=True, exist_ok=True)
shutil.copy2(source_config, target_config)
for source in source_reports.iterdir():
    if source.is_file():
        shutil.copy2(source, target_reports / source.name)
for root, dirs, files in os.walk("/app/data"):
    os.chown(root, 10001, 10001)
    for name in dirs + files:
        os.chown(os.path.join(root, name), 10001, 10001)'
```

示例只复制旧报告目录的直接子文件，与当前迁移器的扫描范围一致。若旧报告存在多级目录，请先按不会重名的批次整理；不要覆盖新版已经生成的报告。

### 8.3 执行一次性迁移

使用 Compose 中已有的登录和数据卷配置，只覆盖旧路径：

```bash
docker compose --env-file .env -f docker-compose.yml run --rm --no-deps \
  -e LLM_BENCHMARK_LEGACY_CONFIG=/app/data/legacy/api_configs.json \
  -e LLM_BENCHMARK_LEGACY_REPORTS=/app/data/reports \
  --entrypoint python \
  llm-benchmark \
  -c 'from benchmark_server.api import create_app; create_app()'
```

该命令只初始化数据库并执行迁移，不启动长期 API/executor 服务。随后正常启动：

```bash
./run.sh
```

如果部署包中的 Compose 服务名被管理员修改，请相应替换命令末尾的 `llm-benchmark`。

## 9. 幂等、去重与失败语义

### 9.1 去重键

迁移记录唯一识别：

```text
源文件绝对路径 + 文件内容 SHA-256
```

因此：

- 同一路径且内容不变：后续扫描跳过；
- 同一路径但内容变化：视为新的迁移尝试；
- 相同内容移动到不同路径：视为不同来源；
- 之前失败的同一路径同内容：可再次尝试并更新失败记录。

### 9.2 单项失败不阻止启动

旧 API 配置或某个报告失败时：

- 错误信息经过脱敏；
- 状态写入 `migration_items`；
- `failed` 计数增加；
- 其他文件继续；
- API 仍继续启动。

这保证迁移失败时工具仍可用于创建新配置和运行新测试，但管理员必须处理 `failed > 0`，不能把“页面能打开”当作迁移完全成功。

### 9.3 原文件不删除

迁移器只读取和登记，不删除原始配置或报告。原文件是失败恢复和人工核对依据。

在确认以下事项前不要删除原文件：

- 诊断中的 `failed` 为 0；
- API 配置可用；
- 重要旧报告可以下载和打开；
- 新任务可以运行并生成新报告；
- 已建立独立备份。

## 10. SQLite schema 迁移与容错启动

### 10.1 正常 schema 升级

`Database.initialize()` 在事务中检查 `schema_migrations`，只应用尚未执行的版本。API 与 executor 共用 SQLite；迁移使用 immediate transaction 避免两个进程同时修改 schema。

### 10.2 普通启动的容错策略

API 正常启动使用 `resilient=True`。如果现有数据库无法打开或 schema 迁移失败：

1. 原数据库重命名为：

   ```text
   llm-benchmark.db.migration-failed-<UTC时间戳>
   ```

2. 对应 `-wal`、`-shm` 文件也一并保留；
3. 创建全新的可运行数据库；
4. 服务继续启动；
5. `/api/diagnostics` 中 `database_recovered` 为 `true`。

该策略优先保证服务可运行，并**不会自动把故障库内容导入新库**。看到 `database_recovered=true` 时，应立即停止创建大量新数据，保存整个数据目录，并对故障库进行独立检查或从部署备份恢复。

### 10.3 更新脚本的严格策略

`update.sh` 在切换新版前先备份整个数据卷，然后以：

```python
Database("/app/data").initialize(resilient=False)
```

执行严格迁移。任何 schema 错误都会让更新失败并触发自动回滚，而不是静默创建空数据库。这与普通启动容错互补：

- 普通启动：优先恢复服务可用性并保留故障文件；
- 正式更新：优先保持旧数据完整，失败即恢复旧版本。

## 11. 更新失败与部署级回滚

通过 `update.sh` 升级时，脚本会在变更数据库前保存：

- 完整数据卷压缩包和 SHA-256；
- `.env`；
- `docker-compose.yml`；
- 旧镜像标签和不可变 ID；
- rollback 镜像标签。

新版镜像加载、数据库迁移、容器启动或健康检查任一步骤失败时，会自动恢复旧数据、配置和镜像并重新验证旧版健康。

详细过程见 [完全离线部署说明](离线部署说明.md)。

## 12. 人工回退原则

如果不是通过 `update.sh` 升级，或自动回滚未完全成功：

1. 停止当前容器，但不要删除数据卷；
2. 复制当前数据卷和部署目录作为故障现场；
3. 找到最后一次已知可用的镜像、`.env`、Compose 和数据备份；
4. 校验备份 SHA-256；
5. 恢复数据卷；
6. 恢复旧配置和旧镜像标签；
7. 使用 `docker compose ... up --detach --no-build` 启动；
8. 验证 `/health/live`、`/health/ready`、登录、任务历史和报告；
9. 保留失败新版日志，完成原因分析后再尝试升级。

不要使用 `docker compose down -v`，也不要在未备份时删除 `llm-benchmark.db.migration-failed-*` 文件。

具体命令和常见故障处理见后续 [故障排查指南](故障排查.md)。

## 13. 迁移验收清单

### 13.1 数据

- [ ] 旧原文件和环境配置已有独立备份；
- [ ] `/api/diagnostics` 中 `legacy_migration.failed` 为 0；
- [ ] `database_recovered` 符合预期，正常迁移应为 `false`；
- [ ] API 配置数量、名称、端点和模型与旧版一致；
- [ ] API Key 未通过列表、日志或错误响应泄露；
- [ ] 重要旧报告可以下载并离线打开；
- [ ] 原文件未被自动删除。

### 13.2 功能

- [ ] 新登录可以使用，旧会话已失效；
- [ ] `smoke` 计划可以连接至少一个迁移后的端点；
- [ ] executor 能领取任务并更新心跳；
- [ ] SSE 实时事件可用，断开后能回退轮询；
- [ ] 新报告可以生成、下载和校验；
- [ ] 服务停止并再次运行后，任务和报告仍存在。

### 13.3 离线与回滚

- [ ] 整个迁移过程不需要访问互联网；
- [ ] 容器启动没有 pull 或 build；
- [ ] 数据卷和 `backups/` 空间充足；
- [ ] 已记录旧镜像标签或源码提交；
- [ ] 已演练一次更新失败自动回滚。

## 14. 迁移完成后的清理

完成验收后可以：

- 将旧明文 API 配置移入受控离线归档，或按组织策略安全销毁；
- 保留重要旧报告及其 SHA-256；
- 把自动化脚本逐步改为 `python3 -m benchmark_cli`；
- 在确认不再回退后清理旧镜像和过期备份；
- 移除旧 Flask、Vue 2、Element UI 和 Streamlit 运行依赖。

清理必须晚于功能验收和回滚演练，且不得删除当前数据卷、`.env`、`secret.key` 或仍被报告索引引用的文件。
