# 故障排查指南

本文用于排查 LLM Benchmark 在完全离线内网中的安装、启动、登录、任务执行、模型连接、实时事件、报告和更新回滚问题。

排障原则：

1. 先保存现场，再尝试恢复；
2. 先确认 Docker、镜像、配置、数据卷和磁盘，再看应用日志；
3. 用小规模 `smoke` 复现，不要在故障状态下继续高并发压测；
4. 日志和截图中不得泄露 API Key、登录密码、会话密钥或真实敏感提示词；
5. **不要执行 `docker compose down -v`，不要删除数据卷。**

## 1. 快速定位流程

按以下顺序执行：

```bash
docker info
docker compose version
docker compose --env-file .env -f docker-compose.yml config
docker compose --env-file .env -f docker-compose.yml ps
docker compose --env-file .env -f docker-compose.yml logs --no-color --tail 200
```

然后检查健康接口：

```bash
curl -i http://127.0.0.1:8080/health/live
curl -i http://127.0.0.1:8080/health/ready
```

登录后打开“设置与诊断”，或请求：

```text
GET /api/diagnostics
```

重点查看：

- `database_recovered`；
- `legacy_migration.failed`；
- `executor.heartbeat_at`；
- 数据目录可写性；
- 磁盘剩余空间；
- Python、平台和发生器资源。

CLI 环境诊断不会访问互联网：

```bash
python3 -m benchmark_cli diagnose --output-dir reports
```

该命令检查本机 Python、平台和输出目录可写性，并明确返回 `network_check: skipped`。

## 2. 收集信息时的脱敏要求

可以收集：

- 容器状态和健康状态；
- 应用版本、镜像标签和镜像 ID；
- 错误类别、HTTP 状态码和 request ID；
- 任务 ID、报告 ID、时间戳；
- 脱敏后的 Base URL 主机和端口；
- 磁盘、CPU、内存和事件循环延迟。

不得直接发送：

- `.env` 全文；
- `LLM_BENCHMARK_PASSWORD`；
- `LLM_BENCHMARK_SESSION_SECRET`；
- OpenAI 兼容端点 API Key；
- `secret.key`；
- 包含敏感输入/输出的完整报告；
- 数据库或更新备份的未加密副本。

查看配置时只读取非敏感项，例如：

```bash
awk -F= '
  $1=="LLM_BENCHMARK_IMAGE" ||
  $1=="LLM_BENCHMARK_CONTAINER_NAME" ||
  $1=="LLM_BENCHMARK_DATA_VOLUME" ||
  $1=="LLM_BENCHMARK_BIND_ADDRESS" ||
  $1=="LLM_BENCHMARK_WEB_PORT" {print}
' .env
```

## 3. 安装脚本找不到镜像归档

### 3.1 现象

```text
[安装失败] 未找到离线镜像归档（images/llm-benchmark-*.tar）
```

或：

```text
[安装失败] 发现多个镜像归档，请通过 LLM_BENCHMARK_IMAGE_ARCHIVE 指定
```

### 3.2 检查

```bash
ls -lh images/llm-benchmark-*.tar llm-benchmark-*.tar llm-benchmark.tar 2>/dev/null
```

脚本查找：

1. `images/llm-benchmark-*.tar`；
2. 根目录 `llm-benchmark-*.tar`；
3. 根目录 `llm-benchmark.tar`。

### 3.3 处理

显式指定唯一归档：

```bash
LLM_BENCHMARK_IMAGE_ARCHIVE='images/llm-benchmark-0.3.0.tar' ./install.sh
```

相对路径以部署目录为基准，也可使用绝对路径。不要通过改名掩盖多个版本混放的问题；应保留清晰版本号和对应校验文件。

## 4. SHA-256 校验失败

### 4.1 现象

```text
镜像归档 SHA-256 不匹配
```

或校验文件没有对应条目。

### 4.2 检查

Linux：

```bash
sha256sum images/llm-benchmark-0.3.0.tar
cat checksums.sha256
```

macOS：

```bash
shasum -a 256 images/llm-benchmark-0.3.0.tar
cat checksums.sha256
```

确认校验文件中的路径为以下任一种：

```text
images/llm-benchmark-0.3.0.tar
llm-benchmark-0.3.0.tar
```

### 4.3 处理

- 重新从可信构建环境导出镜像和校验文件；
- 重新通过离线介质传输；
- 检查介质或文件系统损坏；
- 确认没有把另一个版本的校验文件放在当前目录。

**不要重新生成校验值来“匹配”来源不明的归档。** 校验失败时不得继续加载镜像。

## 5. Docker 或 Compose 不可用

### 5.1 典型错误

```text
Docker 服务不可用或当前用户无访问权限
Docker Compose 插件不可用
```

### 5.2 检查

```bash
docker version
docker info
docker compose version
```

### 5.3 处理

- 启动 Docker daemon；
- 使用具备 Docker 权限的部署账号；
- 安装或启用 Compose v2 插件；
- 如果组织使用 rootless Docker，确认当前 shell 指向正确 socket；
- 不要把旧 `docker-compose` v1 命令与项目脚本混用。

目标服务器无需联网安装应用依赖，但 Docker 和 Compose 本身必须由管理员预先准备好。

## 6. `.env` 缺失或配置无效

### 6.1 典型错误

```text
尚未安装：缺少 .env，请先执行 install.sh
.env 中的 LLM_BENCHMARK_PASSWORD 不能为空
LLM_BENCHMARK_SESSION_SECRET 至少需要 16 个字符
```

### 6.2 处理

首次部署运行：

```bash
./install.sh
```

若 `.env` 被误删但服务数据仍在：

1. 不要重新创建数据卷；
2. 从最近更新备份或受控配置备份恢复 `.env`；
3. 若只能从 `.env.example` 重建，必须恢复原数据卷名、登录配置和会话密钥；
4. 修改权限：

   ```bash
   chmod 600 .env
   ```

5. 验证 Compose：

   ```bash
   docker compose --env-file .env -f docker-compose.yml config >/dev/null
   ```

改变 `LLM_BENCHMARK_SESSION_SECRET` 会让现有登录会话失效，但不会删除数据库。改变数据卷名会让应用看起来像“数据丢失”，实际旧数据卷可能仍存在。

## 7. 本地镜像不存在或 Compose 尝试拉取

### 7.1 现象

```text
本地不存在镜像：...
```

### 7.2 检查

```bash
image=$(awk -F= '$1=="LLM_BENCHMARK_IMAGE" {print substr($0, index($0, "=") + 1)}' .env)
printf 'configured image: %s\n' "$image"
docker image inspect "$image"
docker image ls --digests
```

### 7.3 处理

- 重新执行 `install.sh` 加载正确归档；
- 确认 `.env` 中镜像标签与 `docker load` 输出一致；
- 多标签归档需显式设置 `LLM_BENCHMARK_IMAGE`；
- 正常启动只使用 `./run.sh`，它会传入 `--no-build`；
- `docker-compose.yml` 必须保留 `pull_policy: never` 且不包含 `build:`。

如果日志出现访问 Docker Hub，说明运行的不是当前 Compose/脚本，或管理员覆盖了 Compose 配置。

## 8. 容器无法启动或反复重启

### 8.1 检查状态

```bash
docker compose --env-file .env -f docker-compose.yml ps
docker inspect llm-benchmark --format '{{json .State}}'
docker compose --env-file .env -f docker-compose.yml logs --no-color --tail 200
```

如修改过容器名，请使用 `.env` 中的 `LLM_BENCHMARK_CONTAINER_NAME`。

### 8.2 常见原因

- 登录用户名、密码或会话密钥缺失；
- 数据卷不可写；
- 端口已被占用；
- SQLite 损坏或迁移失败；
- API 或 executor 子进程启动后异常退出；
- 前端构建产物未打入镜像；
- 镜像架构与服务器 CPU 不匹配。

### 8.3 端口占用

```bash
ss -lntp 2>/dev/null | grep ':8080 '
```

可修改：

```dotenv
LLM_BENCHMARK_WEB_PORT=8081
```

然后重新：

```bash
./run.sh
```

### 8.4 镜像架构

```bash
docker image inspect "$image" --format '{{.Architecture}}/{{.Os}}'
uname -m
```

镜像必须在构建时包含目标服务器架构；目标服务器不应在线重新构建。

## 9. `/health/live` 失败

### 9.1 含义

`/health/live` 只表示 FastAPI 进程能否响应。如果连接被拒绝或返回非 200：

- 容器未运行；
- API 子进程已退出；
- 端口映射或绑定地址错误；
- 本机防火墙阻止访问。

### 9.2 排查

```bash
docker compose --env-file .env -f docker-compose.yml ps
docker compose --env-file .env -f docker-compose.yml logs --tail 200
curl -i http://127.0.0.1:8080/health/live
```

如果本机端口不是 8080，用 `.env` 中的实际值。

容器内检查：

```bash
docker exec llm-benchmark python -c \
  "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8080/health/live', timeout=3).read().decode())"
```

容器内成功而宿主机失败，重点检查端口映射、绑定地址和宿主机防火墙。

## 10. `/health/ready` 返回 503

### 10.1 返回结构

就绪接口检查：

- SQLite 可连接；
- 数据目录可写；
- 本地 executor 最近心跳不超过 15 秒。

典型返回：

```json
{
  "status": "degraded",
  "database": "ok",
  "data_dir_writable": true,
  "executor": {
    "status": "stale",
    "heartbeat_at": "2026-01-01T00:00:00+00:00",
    "age_seconds": 30.0,
    "max_age_seconds": 15
  },
  "configuration": "ok"
}
```

### 10.2 `executor.status=missing`

表示 executor 尚未写入过心跳：

- executor 子进程未启动；
- executor 启动后立即退出；
- API 与 executor 使用了不同数据目录。

查看 supervisor 日志：

```bash
docker compose --env-file .env -f docker-compose.yml logs --tail 200
```

源码开发时确认两个进程使用相同变量：

```bash
printf '%s\n' "$LLM_BENCHMARK_DATA_DIR"
```

### 10.3 `executor.status=stale`

表示曾有 executor，但超过 15 秒没有心跳。常见原因：

- executor 崩溃或被系统终止；
- 容器内进程卡死；
- SQLite 长时间不可写；
- 主机资源严重不足。

先保存日志，再优雅重启：

```bash
./stop.sh
./run.sh
```

重启后，遗留运行任务会被标记为中断或按持久队列状态恢复，不应直接修改任务表。

### 10.4 `data_dir_writable=false`

检查卷和目录：

```bash
volume=$(awk -F= '$1=="LLM_BENCHMARK_DATA_VOLUME" {print substr($0, index($0, "=") + 1)}' .env)
docker volume inspect "$volume"
docker compose --env-file .env -f docker-compose.yml logs --tail 200
```

不要把数据卷改成只读。生产镜像以 UID/GID `10001:10001` 运行，卷内文件必须允许该用户读写。

## 11. `run.sh` 等待健康检查超时

`run.sh` 默认等待 120 秒，并在失败时打印最后 80 行日志。

### 11.1 临时延长

只在服务确实启动较慢而非持续报错时使用：

```bash
LLM_BENCHMARK_HEALTH_TIMEOUT=240 ./run.sh
```

### 11.2 不应只延长时间的情况

- executor 持续报错退出；
- 数据目录权限错误；
- 数据库迁移反复失败；
- 端口冲突；
- 镜像架构不匹配。

这些问题延长超时不会修复，应根据日志处理根因。

## 12. 浏览器无法访问

### 12.1 服务器本机可访问，客户端不可访问

检查：

```bash
curl -i http://127.0.0.1:8080/health/live
awk -F= '$1=="LLM_BENCHMARK_BIND_ADDRESS" || $1=="LLM_BENCHMARK_WEB_PORT" {print}' .env
```

如果要让内网客户端访问：

```dotenv
LLM_BENCHMARK_BIND_ADDRESS=0.0.0.0
LLM_BENCHMARK_WEB_PORT=8080
```

还需检查宿主机防火墙和网络 ACL。只开放给需要使用的内网来源。

### 12.2 页面空白或资源 404

- 强制刷新浏览器缓存；
- 查看浏览器开发者工具 Console 和 Network；
- 确认 `/assets/...` 来自当前服务器；
- 检查镜像中 `frontend/dist/index.html` 和静态资源；
- 确认没有部署旧 Vue 2 构建产物覆盖新版。

页面不应请求 CDN、公网字体或遥测地址。

### 12.3 Windows 7 浏览器

重点使用：

- Chrome 109；
- Firefox 115 ESR；
- 不支持 Internet Explorer。

如果旧浏览器缓存了升级前资源，可清理该站点缓存后重试。1366 × 768 下应仍能完成登录、建任务、查看运行状态和下载报告。

## 13. 登录失败

### 13.1 用户名或密码错误

确认使用 `.env` 中实际账号，但不要把密码打印到终端或日志。若忘记密码：

1. 停止服务；
2. 备份 `.env`；
3. 修改 `LLM_BENCHMARK_PASSWORD`；
4. 保持 `LLM_BENCHMARK_SESSION_SECRET` 不变；
5. 权限设为 `600`；
6. 重新运行服务。

```bash
./stop.sh
chmod 600 .env
./run.sh
```

### 13.2 登录成功后立即回到登录页

检查：

- 浏览器是否允许同源 Cookie；
- 是否通过 HTTP 访问但配置了 `LLM_BENCHMARK_SECURE_COOKIE=true`；
- 反向代理是否改变 Host、路径或丢弃 `Set-Cookie`；
- 服务器时间是否严重错误；
- 会话密钥是否在容器重启间变化。

普通 HTTP 内网访问应为：

```dotenv
LLM_BENCHMARK_SECURE_COOKIE=false
```

只有浏览器通过 HTTPS 访问时才设为 `true`。

### 13.3 反复出现 401

- 重新登录获取新会话；
- 检查会话是否超过 `LLM_BENCHMARK_SESSION_HOURS`；
- 确认没有多个实例使用不同会话密钥却共用同一入口；
- 清除该站点 Cookie 后重试。

## 14. 任务一直排队

### 14.1 正常情况

默认一次只运行一个普通压测任务。当前任务未结束时，后续任务保持 `queued` 是预期行为。

### 14.2 异常情况

如果没有运行中任务但队列长期不动：

- 检查 `/health/ready` 中 executor 状态；
- 查看 `/api/diagnostics` 中 heartbeat；
- 检查任务是否因顺序模型比较依赖前一子任务；
- 检查 executor 日志和数据库可写性。

不要通过直接修改 SQLite 把任务强行改成 `running`。

## 15. 任务无法停止

取消是协作式的：API 把任务标记为 `stopping`，executor 在心跳监控中触发取消并让当前请求安全收尾。

若短时间仍显示运行：

1. 等待正在进行的模型请求返回或超时；
2. 查看 executor 心跳是否继续；
3. 检查目标端点是否长时间不响应；
4. 必要时优雅停止整个服务。

```bash
./stop.sh
```

不要直接 `kill -9`，除非优雅停止超时且已保存日志；强制终止会使任务进入 `interrupted`，但持久数据仍应保留。

## 16. OpenAI 兼容端点返回 401 或 403

### 16.1 原因

- API Key 错误、过期或无权限；
- 服务端要求不同认证头；
- 反向代理剥离 `Authorization`；
- API 配置迁移后保存了旧密钥。

### 16.2 处理

- 在“测试资源/API 配置”中重新输入 API Key；
- 不要依赖列表接口回显旧密钥；
- 先用并发 1、请求数 1 的 `smoke` 验证；
- 查看模型服务端日志中的认证失败原因；
- 确认服务兼容标准 `Authorization: Bearer <key>`。

CLI 建议通过环境变量提供密钥，避免进入 shell 历史：

```bash
export LLM_BENCHMARK_API_KEY='replace-me'
python3 -m benchmark_cli run \
  --plan smoke \
  --base-url 'http://10.0.0.20:8000/v1' \
  --model 'internal-model' \
  --requests 1 \
  --concurrency 1 \
  --quiet
unset LLM_BENCHMARK_API_KEY
```

## 17. OpenAI 兼容端点返回 404

### 17.1 Base URL 要求

应填写 API 根地址：

```text
http://10.0.0.20:8000/v1
```

不要填写完整方法地址：

```text
http://10.0.0.20:8000/v1/chat/completions
```

核心会在 Base URL 不以 `/v1` 结尾时自动追加 `/v1`，然后由 OpenAI 客户端调用 `chat/completions`。

### 17.2 其他原因

- 模型服务只实现了 Responses API，没有 Chat Completions；
- 反向代理路径前缀配置错误；
- 服务要求不同 API 版本；
- 模型名不存在时服务错误地返回 404。

项目当前只完善 OpenAI Chat Completions 兼容协议，不会自动切换到其他私有协议。

## 18. 模型名错误或服务返回 400

检查：

- 模型名称是否与服务端注册名完全一致；
- `max_tokens` 是否超过模型上限；
- 服务是否拒绝 `seed`、`stream_options` 或其他兼容参数；
- JSONL 数据集的 `messages` 是否符合角色和内容要求；
- 服务是否只接受非流式请求。

先最小化参数：

```bash
python3 -m benchmark_cli run \
  --plan smoke \
  --base-url 'http://10.0.0.20:8000/v1' \
  --model 'internal-model' \
  --requests 1 \
  --concurrency 1 \
  --output-tokens 16 \
  --non-stream
```

如果最小请求成功，再逐步启用流式、断言、长输入和并发。

## 19. TLS 证书错误

### 19.1 正确处理

优先：

- 把内网 CA 安装到服务器和容器信任链；
- 修复证书过期、主机名不匹配和中间证书缺失；
- 使用证书中包含的 DNS 名称访问。

### 19.2 临时关闭校验

仅在风险明确、网络隔离且用于排查时：

CLI：

```bash
python3 -m benchmark_cli run ... --insecure
```

Web API 配置中关闭 `verify_tls`。

关闭 TLS 校验会降低中间人攻击防护，不应作为长期默认配置，也不能解决服务端协议不兼容。

## 20. 连接拒绝、DNS 或超时

### 20.1 从宿主机测试

```bash
getent hosts model.internal 2>/dev/null || true
curl -v --connect-timeout 5 http://10.0.0.20:8000/v1/models
```

`/v1/models` 不是所有兼容服务都实现；它失败不一定说明 Chat Completions 不可用。

### 20.2 从应用容器测试

应用容器包含 Python，可执行不泄露密钥的连通性检查：

```bash
docker exec llm-benchmark python -c \
  "import socket; print(socket.create_connection(('10.0.0.20', 8000), timeout=5).getpeername())"
```

宿主机可达而容器不可达时，检查 Docker 网络、路由、防火墙和 DNS。容器能建立 TCP 但请求超时时，检查模型排队、生成耗时、请求超时和最大输出 Token。

## 21. 429、5xx 和高错误率

错误分类：

- 429：限流；
- 5xx：模型服务或其网关错误；
- timeout/transport：网络或服务未在时限内响应；
- client：其他 4xx；
- authentication：401/403。

处理顺序：

1. 降低并发或目标 QPS；
2. 使用 `baseline` 或低并发 `fixed_concurrency` 确认单请求稳定性；
3. 检查服务端队列、GPU/CPU、显存和限流配置；
4. 比较发生器资源与目标端资源；
5. 设置持续窗口自动停止，避免错误持续放大。

不要只提高重试次数掩盖容量不足；报告应保留真实错误率和限流结论。

## 22. 模型流式响应失败

模型流式请求与 Web 页面 SSE 是两条不同链路：

- 模型流式：模型端点向压测核心返回 Chat Completions stream；
- 页面 SSE：FastAPI 向浏览器推送持久化任务事件。

模型流式常见问题：

- 服务返回的不是标准 SSE/Chat Completions chunk；
- chunk 缺少 `choices[].delta`；
- 服务不接受 `stream_options.include_usage`；
- 流结束方式或 usage 扩展不兼容；
- 中间代理缓冲或截断流。

先用 `--non-stream` 验证基础请求。若非流式成功而流式失败，应保留脱敏后的协议错误和服务端日志，修复兼容层或模型网关，而不是把失败样本当作成功。

## 23. 页面 SSE 断线或自动切到轮询

### 23.1 现象

运行页显示：

```text
SSE 正在重连
轮询回退 · 2 秒
```

### 23.2 含义

后台任务通常仍在 executor 中继续运行。页面会：

1. 尝试 SSE；
2. 使用最后 sequence 重连；
3. 持续失败后回退到状态轮询。

### 23.3 排查

- 浏览器是否支持 `EventSource`；
- 反向代理是否缓冲 `text/event-stream`；
- 代理读超时是否过短；
- Cookie 是否随 SSE 同源请求发送；
- API 日志中 `/api/tasks/<id>/events` 是否返回 401/5xx；
- 任务事件 sequence 是否持续增长。

轮询能获得终态时，不要停止正在执行的压测；先修复代理或浏览器链路。

## 24. 实时指标不更新但任务在运行

可能原因：

- 事件尚未达到 executor 批量写入大小；
- 模型首个 Token 很慢；
- SSE 断开且轮询尚未开始；
- SQLite 写入受阻；
- executor 心跳正常但 runner 卡在模型请求。

检查任务状态、事件数量、executor 心跳和模型端日志。若单请求超时设置很大，页面可能在等待首个请求结束后才出现更多指标。

## 25. 报告生成或下载失败

### 25.1 任务尚无结果

按需生成 CSV/XLSX/HTML 前，任务必须存在持久化结果。运行中、失败且无结果的任务会返回冲突错误。

### 25.2 报告文件不存在

报告索引存在但文件被移动、删除或未正确迁移时，下载返回 404。检查：

```bash
image=$(awk -F= '$1=="LLM_BENCHMARK_IMAGE" {print substr($0, index($0, "=") + 1)}' .env)
volume=$(awk -F= '$1=="LLM_BENCHMARK_DATA_VOLUME" {print substr($0, index($0, "=") + 1)}' .env)
docker run --rm --network none --entrypoint python \
  --volume "$volume:/app/data:ro" "$image" \
  -c 'from pathlib import Path
root = Path("/app/data/reports")
print("exists=", root.exists())
for path in sorted(root.glob("*"))[:50]:
    print(path.name, path.stat().st_size)'
```

命令会从 `.env` 读取镜像和数据卷名称。不要把任意宿主机绝对路径写入报告索引；下载接口会拒绝报告根目录外的路径。

### 25.3 权限或磁盘

报告目录不可写、磁盘满或 inode 用尽都会导致生成失败。参见“磁盘空间不足”。

### 25.4 HTML 离线打开

新版 HTML 应自包含，不应请求外部脚本、样式或字体。浏览器打开后若仍出现公网请求，确认下载的是新版制品而不是旧版报告。

## 26. 磁盘空间不足

### 26.1 检查

```bash
df -h
df -i
docker system df
du -sh backups 2>/dev/null || true
docker volume inspect llm-benchmark-data
```

### 26.2 处理优先级

1. 停止新的压测任务；
2. 保存当前日志和任务信息；
3. 清理明确不再需要的旧 Docker 构建缓存或无关镜像；
4. 按备份策略归档过期更新备份；
5. 在 Web 中删除确认不需要的报告，让索引和文件同步更新；
6. 扩容 Docker 数据目录或宿主机文件系统。

不要直接进入数据卷批量删除文件；不要删除当前数据库、`secret.key` 或最近一次可用更新备份。

## 27. SQLite 锁、损坏或自动恢复

### 27.1 锁竞争

SQLite 使用 WAL 和 30 秒 busy timeout。持续出现 `database is locked` 通常意味着：

- 数据卷或底层文件系统不适合 SQLite 锁语义；
- 外部工具长时间占用数据库；
- 人工脚本开启事务后未结束；
- 资源严重不足导致事务长期阻塞。

不要在服务运行时用 SQLite GUI 修改数据库。

### 27.2 `database_recovered=true`

表示普通启动时原数据库迁移失败，系统已把故障库保留为：

```text
llm-benchmark.db.migration-failed-<UTC时间戳>
```

并创建了新数据库以保证服务可启动。

此时：

1. 停止继续写入大量新数据；
2. 保存整个数据卷；
3. 查看诊断中的恢复信息和日志；
4. 优先从最近一次已验证的 `update.sh` 备份恢复；
5. 不要删除故障库及其 `-wal`、`-shm` 文件。

## 28. 旧配置或旧报告迁移失败

诊断中：

```text
legacy_migration.failed > 0
```

检查：

- `backend/api_configs.json` 是否是合法 JSON 数组；
- 配置字段是否为对象；
- 报告 JSON 是否可解析；
- 旧路径在当前进程/容器内是否可见；
- 数据目录是否可写；
- 迁移错误是否已脱敏记录。

单项失败不会阻止启动，原文件也不会删除。修复源文件或路径后重新启动可再次尝试。详细说明见 [旧版本迁移说明](迁移说明.md)。

## 29. `update.sh` 在备份前失败

在 `ROLLBACK_ARMED` 前失败通常不会停止旧版本，例如：

- `.env` 缺失；
- 旧镜像或数据卷不存在；
- 新归档缺失；
- SHA-256 不匹配；
- 新旧镜像内容相同。

处理错误后重新执行即可。不要因为更新未开始就手工删除旧容器或卷。

## 30. `update.sh` 备份、迁移或健康检查失败

更新进入保护阶段后会自动：

- 保存新版本日志；
- 恢复完整数据卷；
- 恢复 `.env` 和 Compose；
- 恢复旧镜像标签；
- 重启旧版本；
- 验证旧版本健康。

成功信息：

```text
[回滚] 已恢复旧数据、旧配置和旧镜像，旧版本健康检查通过。
```

对应现场位于：

```text
backups/update-<UTC时间戳>/
```

检查：

```bash
ls -lah backups/update-*/
cat backups/update-*/old-image.txt
cat backups/update-*/rollback-image.txt
```

不要在确认旧版健康前删除 rollback 镜像标签或备份目录。

## 31. 自动回滚也未完全成功

### 31.1 先保护现场

1. 记录脚本输出中的备份目录；
2. 不要再次运行 `update.sh`；
3. 不要删除容器、卷、镜像或备份；
4. 保存：
   - 当前 `.env`；
   - 当前 `docker-compose.yml`；
   - `docker compose ps`；
   - 最后 200 行日志；
   - `docker image ls --no-trunc`；
   - `docker volume inspect`。

### 31.2 校验数据备份

假设：

```bash
backup='backups/update-20260822T010203Z'
```

Linux：

```bash
test "$(cat "$backup/data.tar.gz.sha256")" = \
  "$(sha256sum "$backup/data.tar.gz" | awk '{print $1}')"
```

macOS：

```bash
test "$(cat "$backup/data.tar.gz.sha256")" = \
  "$(shasum -a 256 "$backup/data.tar.gz" | awk '{print $1}')"
```

校验不通过时不要恢复该压缩包，应先从其他备份或介质找回完整文件。

### 31.3 人工恢复旧配置和数据

以下步骤会覆盖当前数据卷，只有在已复制故障现场且数据备份校验通过后执行。

恢复配置：

```bash
cp "$backup/.env" .env
chmod 600 .env
cp "$backup/docker-compose.yml" docker-compose.yml
```

读取名称：

```bash
volume=$(awk -F= '$1=="LLM_BENCHMARK_DATA_VOLUME" {print substr($0, index($0, "=") + 1)}' .env)
old_image=$(cat "$backup/old-image.txt")
rollback_image=$(cat "$backup/rollback-image.txt")
```

停止当前容器，但保留卷：

```bash
docker compose --env-file .env -f docker-compose.yml down --remove-orphans
```

确认 rollback 镜像仍存在：

```bash
docker image inspect "$rollback_image"
```

恢复数据卷：

```bash
docker run --rm --user 0:0 --network none \
  --entrypoint python \
  --env BACKUP_FILE=data.tar.gz \
  --volume "$volume:/data" \
  --volume "$(pwd)/$backup:/backup:ro" \
  "$rollback_image" \
  -c 'import os, pathlib, shutil, tarfile
root = pathlib.Path("/data")
for child in root.iterdir():
    if child.is_dir() and not child.is_symlink():
        shutil.rmtree(child)
    else:
        child.unlink()
with tarfile.open("/backup/" + os.environ["BACKUP_FILE"], "r:gz") as archive:
    archive.extractall(root, filter="data")'
```

恢复旧镜像标签并启动：

```bash
docker image tag "$rollback_image" "$old_image"
./run.sh
```

最后验证：

```bash
curl -i http://127.0.0.1:8080/health/live
curl -i http://127.0.0.1:8080/health/ready
docker compose --env-file .env -f docker-compose.yml logs --tail 200
```

如果 rollback 镜像已经丢失，不要用未知镜像恢复。应重新加载与旧版本完全一致的离线镜像归档，再恢复数据。

## 32. 更新后旧数据“消失”

先检查 `.env` 中数据卷名是否变化：

```bash
awk -F= '$1=="LLM_BENCHMARK_DATA_VOLUME" {print}' .env
docker volume ls
docker volume inspect llm-benchmark-data
```

常见原因是新 `.env` 指向了新卷，而旧卷仍在。不要初始化或删除任何卷，先对比更新备份中的 `.env`。

如果 `database_recovered=true`，则可能是 schema 迁移失败后创建了新数据库；按 SQLite 恢复章节处理。

## 33. CLI 无浏览器测试失败

### 33.1 先检查环境

```bash
python3 -m benchmark_cli diagnose --output-dir reports
python3 -m benchmark_cli --help
python3 -m benchmark_cli run --help
```

### 33.2 稳定最小测试

```bash
export LLM_BENCHMARK_BASE_URL='http://10.0.0.20:8000/v1'
export LLM_BENCHMARK_MODEL='internal-model'
export LLM_BENCHMARK_API_KEY='replace-me'

python3 -m benchmark_cli run \
  --plan smoke \
  --requests 1 \
  --concurrency 1 \
  --output-tokens 16 \
  --format json \
  --output-dir reports/smoke
```

检查退出码：

```bash
status=$?
printf 'exit_code=%s\n' "$status"
```

详细退出码、JSON 输出和阈值行为见 [CLI 使用说明](CLI使用说明.md)。

### 33.3 JSONL 数据集

```bash
python3 -m benchmark_cli validate-dataset /path/to/dataset.jsonl
```

请替换为真实文件。验证失败时按提示修复具体行，不要在高并发任务中边运行边试错数据集。

## 34. 性能结果异常但没有明显请求错误

### 34.1 先区分目标瓶颈和发生器瓶颈

检查：

- 发生器 CPU、内存；
- 事件循环延迟；
- 队列 backlog 和增长；
- 目标服务 GPU/CPU/显存；
- 网络带宽和连接数；
- 输入/输出 Token 分布；
- 流式和非流式差异。

### 34.2 复测顺序

1. `smoke` 验证协议；
2. `baseline` 获取单并发基线；
3. 低并发 `fixed_concurrency`；
4. `stepped` 找容量拐点；
5. `constant_rate` 观察排队；
6. `stability` 验证长期波动。

固定数据集、种子和样本顺序，否则不同测试的差异可能来自负载变化而不是模型性能。

### 34.3 同步比较

同步比较会同时增加多个模型负载。确认页面和报告中的：

- 每模型负载；
- 聚合负载；
- `independent` 或 `shared` 资源语义；
- 共享资源竞争警告。

共享 GPU、网关或网络时，优先使用顺序比较获得更易解释的结果。

## 35. 日志中出现公网请求

运行时不应访问：

- Docker Hub；
- PyPI；
- npm registry；
- CDN；
- 公网字体；
- 遥测服务。

若出现公网请求：

1. 确认使用的是生产镜像而非开发服务器；
2. 检查 Compose 是否被覆盖为 `build` 或 `pull`；
3. 检查前端 Network 是否加载远程资源；
4. 检查模型 Base URL 是否误填为公网地址；
5. 检查反向代理或系统级监控注入；
6. 在隔离网络重新执行安装和启动验收。

唯一预期的业务网络访问是管理员明确配置的内网 OpenAI 兼容模型端点。

## 36. 禁止操作

除非已经完成独立备份和明确恢复方案，不要执行：

```bash
docker compose down -v
docker volume rm llm-benchmark-data
rm -rf backups
rm -f .env
rm -f /app/data/llm-benchmark.db
```

也不要：

- 在服务运行时手工编辑 SQLite；
- 把 `.env`、数据库或 `secret.key` 上传到公共问题追踪系统；
- 用 `--insecure` 长期绕过 TLS；
- 在校验失败后强行加载未知镜像；
- 在旧版本尚未恢复健康时继续重复执行 `update.sh`；
- 直接修改任务状态来跳过队列或同步比较限制。

## 37. 排障完成后的验证

每次修复后至少验证：

```bash
curl -f http://127.0.0.1:8080/health/live
curl -f http://127.0.0.1:8080/health/ready
docker compose --env-file .env -f docker-compose.yml ps
```

并完成：

- 登录；
- 创建 1 请求、并发 1 的 `smoke`；
- executor 领取并完成任务；
- 实时事件或轮询可看到终态；
- JSON 报告可生成和下载；
- 服务停止再启动后数据仍存在；
- 日志中没有凭据和公网资源请求。
